# NX-10 soak 예약 통제 (2026-09-16 사고 기록 + `soak_control.sh`)

이 문서는 **예약을 거는 일·취소하는 일·그것이 실제로 그렇게 됐는지 확인하는 일**의 소유자다.
값(지문·시각)의 소유자는 [soak-schedule.txt](./soak-schedule.txt) 와 [GATE_LEDGER.md](GATE_LEDGER.md) §12 다.

## 0. 도구

```bash
cd <repo>
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh status    # 예약 상태(exit 0 = 건강)
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh arm       # 22:00 예약(지문은 지금 트리에서 계산)
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh cancel    # 취소 — **죽었는지 검증**한다
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh orphans   # 잠금 밖에서 도는 예약 탐지
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh preflight # 발화 전: 이 밤을 태울 준비가 됐는가(예약 11개 · 즉시 시작 7개 점검)
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh run        # 기다리지 않고 **지금** 시작(같은 preflight 통과 필요, 이미 예약이 있으면 거부)
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh harvest    # 끝날 때까지 기다렸다가 회수 판정까지(`--detach` 면 창이 죽어도 산다)
bash docs/qa/2026-09-16-followup/nx10/soak_control.sh selftest  # 임시 디렉터리에서 75개 검사
```

`status` 는 **모드를 먼저 가른다** — 대기 중(`armed`)이면 “단일 예약 · 지문 일치”를, **실행 중**(`RUNNING`, 즉시 시작)
이면 “시작 지문 == 현재 트리”를 판정한다. 실행 중에는 예약 잠금이 없으므로, 종전처럼 `armed` 를 요구하면
돌고 있는 soak 을 보면서도 `ATTENTION` 을 뱉는다(§3d).

| 무엇을 보장하는가 | 어떻게 |
|---|---|
| 예약은 **하나만** | `mkdir` 원자성으로 `.soak-arm.lock` 을 잡고, 주인이 살아 있으면 두 번째 예약은 `exit 2` 로 거부 |
| 취소가 **진짜 취소** | 트리(래퍼·bash·heartbeat) 단위로 SIGTERM → 유예 후 SIGKILL 승격 → **재검색해 0건을 확인**하고 그 문장을 증거에 남긴다 |
| 예약된 지문은 **지금 트리** | `arm` 이 직접 계산한다(고정 해시를 손으로 넘기지 않는다). 계산 실패(`UNVERIFIED`)면 예약을 거부 |
| 재는 것이 **커밋된 후보** | `preflight` 가 `현재 트리 지문 == HEAD 트리 지문`을 확인한다(`tree_fingerprint_of_commit`). 아니면 8시간이 끝나도 결과를 후보에 귀속할 수 없다 |
| 그 밖의 전제도 발화 **전에** | `preflight` 는 인터프리터가 `ga_gate` 를 임포트하는가 · 러너·측정 자산 · `/tmp` 여유(기본 2048 MiB) · 이미 도는 soak 없음까지 보고, 하나라도 어긍나면 `exit 1` |
| 8시간은 **한 번만** | 러너가 별도 잠금(`.soak-run.lock`)을 잡는다 — 예약이 둘로 늘어나도 soak 은 둘로 늘어나지 않는다 |
| **쓰다가 507 로 멈추지 않는가** | `preflight` 가 60초 프루브의 journal 쓰기량을 8시간으로 투영해 **hard cap 과 비교**한다(§3e). 넘치면 밤을 태우기 전에 `exit 1` |
| 회수가 **사람의 시각에 묶여 있지 않다** | `harvest` 가 끝날 때까지 기다렸다가 회수 판정기까지 돌리고 그 `exit` 를 그대로 전한다. 아직 돌고 있으면 `--no-wait` 는 `exit 4` 로 거부한다(러너는 종료 시에만 `end_*`·`exit` 를 쓰므로 지금 판정하면 **옛 블록**을 읽는다) |
| 살아 있지만 **멈춘** 실행을 도는 것으로 보지 않는다 | `harvest` 가 마지막 쓰기(작업디렉터리·로그) 이후 경과를 매 폴링마다 보고, `NX10_HARVEST_MAX_STALL`(기본 1800초)을 넘으면 `exit 6` 으로 내려온다 — 실측 사고(§3f)가 정확히 그 모양이었다 |
| 시작 포장이 사람 손에 달려 있지 않다 | `run` 이 발화 전 **같은 preflight** 를 돌리고(실패하면 `exit 2`), 이미 예약이 걸려 있으면 거부하며, 예약과 **같은 포장**(`screen` + `caffeinate -i`)으로 띄우고 실행 잠금·프로세스로 시작을 확인한다 |

`arm` 은 `screen -dmS nx10soak` 을 쓰고, 예약 스크립트는 **대기 중**에는 잠금을 잡고 있다가 발화 직전
지문 확인을 통과하면 잠금을 놓고 러너로 `exec` 한다. 그래서 `status` 의 잠금 상태는 곧 "대기 중인가"다.

## 1. 사고: 취소했다고 기록한 예약 3건이 살아 있었다 (2026-09-16)

- 08:20Z·09:47Z·10:26Z 에 건 예약을 각각 `screen -S nx10soak -X quit` 으로 취소하고 **`soak-exit.txt`
  에 "시작 전 대기 중이었고 시작하지 않았다"고 기록**했다. 그런데 `pgrep -fl schedule_nx10_soak` 로
  확인하니 **네 벌이 모두 살아서 대기 중**이었다(10:47Z 예약 포함). 원인은 `login -pflq` 래퍼다 —
  화면을 닫으면 자식이 SIGHUP 을 받지만 이 래퍼는 무시하고 계속 산다. 즉 **취소 기록이 사실이 아니었다**.
- 그대로 두면 22:00 에 4개가 동시에 깨어난다. 그중 3개는 기대 지문이 낡아 드리프트로 스스로 멈추지만
  (그것이 설계다), 같은 `soak-schedule.txt`·`soak-schedule.log` 에 동시에 append 하므로 **기록이
  뒤섞이고**, 그 뒤 누가 같은 지문으로 재장전하면 **soak 두 개가 동시에** 돌 수 있었다(포트·작업
  디렉터리·리포트 충돌 → 어느 쪽 결과도 후보에 쓸 수 없다).
- 조치: 세 트리(래퍼+bash+heartbeat)를 SIGTERM 으로 종료하고 **`ps` 로 소멸을 확인**했다.
  10:47Z 예약도 편집을 안전하게 하려고 같이 내렸다(bash 는 실행 중인 스크립트를 조금씩 읽으므로
  대기 중인 스크립트를 편집하는 것은 그 자체로 위험하다).
- **탐지가 늦은 이유**: heartbeat 로그가 15분마다 여러 줄씩 찍혀 있어(아래 §3-③) 여러 프로세스가
  쓰고 있다는 사실이 로그에서 보이지 않았다. 지금은 `status` 가 **예약 건수와 고아 수**를 따로 말한다.

## 2. 같은 점검에서 나온 두 번째 결함: 지문 검사가 PATH 에 의존했다

예약 스크립트의 시작 지문 검사는 `python -c "… import ga_gate …"` 를 썼다. 이 기기에서 `python` 은
miniforge 3.13 이라 통과하지만 **`/usr/bin/python3` 는 3.9.6** 이고 `ga_gate.py` 의 `type X = …`
문법을 파싱하지 못한다. PATH 순서가 조금만 달랐다면 검사가 `UNVERIFIED` 를 내고 **22:00 에 아무것도
하지 않고 중단**했을 것이다(8시간 창을 그냥 잃는다). 그래서 ① 지문 계산을 `$REPO/.venv/bin/python`
(없으면 `python3`)으로 고정하고 ② **`UNVERIFIED` 는 불일치보다 먼저** 막도록(별도 사유로 기록하고
`exit 3`) 바꿨다 — 계산 실패를 "그냥 진행"으로 넘기지 않는다. 러너의 시작·종료 지문도 같은 파이썬을 쓴다.

## 2b. 세 번째 결함: 회수 판정기가 **첫 예약**을 기대값으로 읽었다

`soak-schedule.txt` 는 예약할 때마다 블록을 **덧붙인다**(재장전·취소 기록도 쌓인다). 그런데 회수
판정기 `scripts/collect_soak_result.py` 의 `expected_fingerprint()` 는 `re.search`(= **첫 매치**)로
기대 지문을 읽었다. 2026-09-16 파일의 첫 값은 `157311cf…`(08:20Z 예약)이고 현재 예약은 `92fcaeb5…`
(11:39Z)이었으므로, 그대로 두면 **밤새 정상으로 끝난 8시간 실행이 ③(기대 == 시작)에서 거짓 FAIL** 로
판정됐다. 실측(판정기 실행): 종전 `기대=157311cf…`, 수정 뒤 `기대=92fcaeb5… (예약 이력 5건 중 마지막)`.

이것은 이 카드가 가장 자주 겪은 사고와 같은 종류다 — **지표는 통과인데 귀속이 어긋나 판정 근거가
사라지는 것**(EX-05). 그래서 `--expected-fingerprint` 로 사람이 우회하는 길을 남겨 두되, **기본 경로를
고쳤다**: 마지막 예약을 쓰고, 어느 예약을 썼는지(이력 몇 건 중 마지막인지)를 판정 출력에 문장으로
남긴다. 이빨은 계약 시험(`tests/test_soak_recovery_judge.py::test_schedule_reader_uses_the_latest_reservation`)
과 자기시험 3건(이력 3건 → 마지막 · 이력 없음 → `UNVERIFIED` · `previous_expected_fingerprint:` 는
기대값이 아님)이 고정한다. 판정기 자기시험은 **9/9**.

**대가**: 판정기는 `scripts/`(= 지문 대상)에 있으므로 이 수정은 지문을 `92fcaeb5…` → `322b4d3b…` 로
옮겼고, 그래서 오늘 8시간 실행은 **커밋(1bd95e7d) → 필수 23개 재측정(promote004) → 재장전** 순으로
다시 세워야 했다. 수정한 판정기로 판정되지 않는 soak 은 남길 이유가 없다.

## 3. 자기시험이 잡은 것 (설계를 고친 자리)

`selftest` 는 **본 저장소의 예약을 건드리지 않고** 임시 디렉터리에서 사고를 재현한다(32개 검사,
약 2분, `32/32 passed`). 첫 실행은 `10/17` 이었고 실패는 전부 **도구 쪽 결함**이었다:

| 증상 | 진짜 원인 | 고침 |
|---|---|---|
| ③④ 취소가 아무것도 죽이지 못함 | macOS 에 GNU `tac` 이 없다 → 역순 파이프가 비어 `kill` 이 한 번도 안 돌았는데 "성공"으로 계산 | `awk` 역순 + **트리를 열거하지 못하면 죽었다고 주장하지 않는다** |
| ⑥ `arm` 이 "건강"이라 하지 않음 | 예약 1건이 프로세스 **2개**(`login -pflq` 래퍼 + `bash`)로 보이는데 "정확히 1개"를 요구 → 영원한 거짓 경보 | 일치 프로세스가 아니라 **최상위(루트)** 를 세고, 잠금 주인이 그 트리 안에 있으면 정상으로 본다(오늘 아침 4건이 12개 프로세스로 보였다) |
| 첫 실행이 300초 타임아웃 | 가짜 프로세스가 호출자의 stdout 파이프를 물려받아 살아 있는 동안 EOF 가 안 옴 | 시험용 프로세스 출력은 파일로 보낸다 |
| ⑤ heartbeat 로그 중복 | `remaining % 900 < 60` 은 60초 동안 참이라 15분마다 4줄이 찍혔다(주석의 "중복 방지"와 반대) | 버킷이 바뀔 때만 한 줄 — 로그가 중복 프로세스를 숨기지 않게 |

시험 항목: ① 살아 있는 예약이면 `arm` 거부 ② `UNVERIFIED` 면 예약 거부 ③ 취소 후 잔존 0건 검증
④ SIGTERM 무시 프로세스도 KILL 승격으로 종료 ⑤ stale 잠금은 `stale` 로 표기(속이지 않음)
⑤b 잠금 주인을 품은 예약은 고아가 아니다 ⑥ 전체 수명주기(진짜 예약 스크립트 + 스텁 러너:
잠금 → 발화 → 잠금 해제 → 러너 1회 → 시작 지문 기록) ⑦ 러너의 동시 실행 거부(`exit 5`, 리포트 미생성)
⑧ `preflight` 7건 — 건강한 예약 0 · 후보 귀속(현재 트리 == HEAD)까지 보는가 · 여유 공간 미달 1 ·
이미 도는 soak 1 · 지문 불일치 1 · 유령 잠금 1(각각 해당 항목을 문장으로 지목하는지까지).

## 3b. 네 번째 단계: preflight 에 **처리량 하한**을 추가했다 (2026-09-17)

왜 필요한가: 직전 8시간 실행은 **60초에 2,978 ops(49.6 ops/s)** 를 내고도 preflight 10개를 전부
통과했고, 그대로 8시간을 돌아 **70,430 ops(2.45 ops/s)** 로 끝났다(SC-6 RSS FAIL). 즉 종전
preflight 는 "돌아갈 것인가"는 물었지만 **"이 작업량이 8시간에 의미 있는 양을 하는가"는 묻지 않았다**.
그래서 `run`/`preflight` 가 시작 전에 **60초 SC-6 프루브**를 임시 디렉터리에서 돌리고 처리량을 잰다.

```
  [OK  ] 처리량 하한 ≥ 133 ops/s — 실측 443 ops/s(60초 26,632 ops · 8시간 외삽 ≈12,783,360 ops)
```

- 기준은 **비율**(`NX10_PREFLIGHT_MIN_OPS_PER_SEC`, 기본 **133 ops/s**)이다. 근거(실측): 고친 코드
  **486 ops/s**(60초 29,180) · 고장난 코드 **49.6 ops/s**(그 실행의 평균은 2.45 ops/s). 133/s 는 고친
  코드의 27%, 고장난 60초 값의 2.7배 — 기계 속도 차이를 견디는 폭이다.
- 프루브 길이는 `NX10_PREFLIGHT_PROBE_SECONDS`(기본 60초), 생략은
  `NX10_PREFLIGHT_SKIP_THROUGHPUT=1`(자기시험은 그 문을 쓴다 — 60초 프루브는 시험을 느리게 만든다).
- 실패하면 **프루브 로그 경로를 남기고** 임시 디렉터리를 지우지 않는다(다음 사람이 원인을 본다).

**이 항목을 만들면서 실제로 걸린 두 함정 — 다음 사람을 위해 적는다.**

1. **성공 판정을 exit code 로 하면 안 된다.** `val02_staging.py` 는 `--scenarios SC-6` 만 돌리면
   리포트에 `missing_required: SC-1..SC-5` 를 담고 `main()` 이 **exit 1** 을 낸다(필수 시나리오 미실행을
   숨기지 않기 때문). 나는 처음에 `if …; then` 으로 성공을 판정해 **모든 프루브를 실패로 읽었고**,
   자기시험이 그것을 "실측 0 ops" 로 보여주었다. 그래서 판정은 **리포트가 나왔는가**(JSON 에서
   `completed_ops` 를 읽어낼 수 있는가)로 바꾸었고, 리포트조차 없으면 그 사유(exit code 포함)를 문장으로 남긴다.
2. **절대 개수 기준은 프루브 길이를 바꾸는 순간 거짓이 된다.** 처음엔 하한을 `NX10_PREFLIGHT_MIN_OPS=8000`
   (60초 기준)로 두었는데, 자기시험이 5초 프루브를 쓰자 같은 기준이 정상 동작을 실패로 만들었다.
   그래서 하한을 ops/s 비율로 바꾸고, 출력에 **두 단위를 함께**(실측 ops/s · 8시간 외삽 ops) 적는다.
   가짜 원인을 가리키는 지표는 없느니만 못하다.

자기시험은 **36 → 43건**이 되어 프루브의 통과·미달·"리포트 없음" 세 경로를 모두 밟는다(43/43).

## 3d. 다섯 번째 결함: 도구가 **돌고 있는 soak 을 오탐**했다 (2026-09-17)

수정 뒤 8시간 재실행이 도는 동안 `soak_control.sh status` 를 돌려보니 `판정: ATTENTION` 이었다 — 도구가
**정상 실행 중인 soak 을 문제로 보고 있었다.** 두 가지가 겹쳤고, 둘 다 교훈이 다르다.

① **`status` 가 “예약”과 “실행”을 구분하지 않았다.** `run`(즉시 시작)으로 띄운 soak 은 예약 잠금이
없으므로 `armed` 를 요구하는 판정은 **상시 거짓 경보**가 된다(실측 `2026-09-16T23:28Z`: 실행 중인데 ATTENTION).
상시 거짓 경보는 다음 사람이 그 줄을 안 읽게 만든다 — 오늘 이 카드가 계속 싸워 온 것과 같은 종류다.
→ 모드를 먼저 가르고, 실행 중이면 **시작 지문 == 현재 트리**를 판정한다(경과·남은 초·종료 예정도 함께 보여준다).

② **자기시험이 환경에 결합돼 있었다.** 3일 전 추가한 preflight 항목 “다른 soak 실행 없음” 은 `val02_staging.py`
를 **기계 전체**에서 찾는다(그 판단은 옳다 — 두 개가 동시에 돌면 서로의 처리량·RSS 측정을 오염시킨다).
그런데 그 이름을 시험이 통제하지 않아서, 진짜 soak 이 도는 동안에는 시험 픽스처가 **전부 실패**했다:
`SOAK_CONTROL_SELFTEST: 47/50 passed` — 실패 3건이 모두 이 하나 때문이었다(preflight 2건 · `run` 거부 사유 1건).
→ 하네스 이름을 `NX10_SOAK_PROC_PATTERN` 으로 빼서 시험이 통제하고, "돌고 있는 soak 을 잡는가"를
**결정적으로** 고정했다(가짜 soak 프로세스를 띄워 preflight 가 pid 를 지목하는지까지 본다). 이제 시험은
**진짜 soak 이 도는 중에도** 의미를 가진다(52/52).

같이 잡은 자잘한 것: 새 픽스처가 공용 변수 `$d` 를 바꿔 **뒤 픽스처의 전제(스케줄러 자산 존재)를 깨뜨린**
것(유일한 잔여 실패의 정체 — 시험끼리 상태를 공유하지 않게 고쳤다).

**이 두 결함은 soak 의 결과에 영향을 주지 않는다** — 도구는 `docs/` 안에 있고, 실행 중 트리 지문은 시작값
`98855031…` 그대로였다(수정 전후 `status` 로 확인).

## 3e. 여섯 번째 결함: 수정이 만든 **새 사각지대** — 쓰기량이 기본 hard cap 을 넘었다 (2026-09-17)

수정 뒤 8시간 재실행(§3c)이 47분쯤 돌았을 때 로그에 한 줄이 보였다:

```
Conversation journal above soft cap: … size=64.00 MB soft_cap=64.00 MB hard_cap=512.00 MB
(writes continue; no automatic pruning — see ADR-DAT-02 Context 8)
```

실물을 재보니 journal 이 **452 MiB**(중단 시점 439 MiB)였고, **160 KB/s** 로 자라고 있었다 —
**8분 뒤에 기본 hard cap(512 MiB)을 넘긴다**. 넘긴 뒤에 벌어지는 일이 이 사고의 핵심이다:

- 제품은 ADR-DAT-02 대로 **자동 prune 없이** append 를 `ConversationHistoryQuotaExceededError`(507)로
  거절한다(지우지 않는다 — 그 결정 자체는 옳다).
- 하네스는 그 예외를 `errors += 1` 로 세고, SC-6 의 `pass` 조건에 **`errors == 0`** 이 들어 있다.
- 즉 8시간 실행이 **제품 결함이 아니라 설정 때문에 거짓 FAIL** 로 끝났을 것이다 — 이 카드가
  반복해 싸워 온 것과 같은 종류(“돌리다 만 것”과 “다른 이유로 빨개진 것”을 구분하지 못하는 FAIL)다.

**왜 지금 생겼는가**: 꼬리 창 수정으로 append 가 20배 빨라졌다(§10, `tail()` 265 ms → 0.04 ms).
직전 FAIL 실행의 8시간 journal 은 **24.4 MB** 였으므로 기본 캡과 부딪힐 일이 없었고, 바로 그 때문에
**어제의 리허설·점검이 이 벽을 보지 못했다.** 처리량 하한(§3b)과 정확히 쌍둥이 사각지대다:
“빠르게 도는가”만 묻고 **“그 속도로 쓰면 어디서 멈추는가”**를 묻지 않았다.

**조치 ① 실행 중단(48분)**: `kill -TERM <harness pid>` → 러너가 `exit: 143` · `end_fingerprint 98855031…`
(시작과 동일 — 트리는 안 흔들렸다)을 기록했다. 스스로 끝난 실행이 아니므로 판정 대상이 아니고,
그 사실을 `soak-exit.txt` 에 러너 기록으로 남겼다(운영자 해설은 `#` 줄로 구분).

**조치 ② 러너가 캡을 정하고 기록한다**: `run_nx10_soak.sh` 가 `AGK_CONVERSATION_JOURNAL_HARD_CAP_MB=8192`
를 export 한다(8시간 예상 쓰기량 ≈4.5 GB 가 여유 있게 들어간다). **soft cap 은 기본(64 MiB)을 그대로 둔다** —
경고와 `journals_over_soft_cap` 관측이 그대로 살아 있어야 “journal 이 얼마나 자랐는가”를 잃지 않는다.
기록에 `command: AGK_CONVERSATION_JOURNAL_HARD_CAP_MB=8192 …` 와 **유효 캡을 해석한 줄**(`retention_caps:
soft=64MiB hard=8192MiB`)을 함께 남긴다 — 측정 설정도 증거다(숨기지 않는다).

**조치 ③ preflight 가 이 벽을 묻는다**: 프루브가 만든 journal 바이트를 8시간으로 투영해(cap 의 90% 미만을 요구)
넘치면 시작 전에 `exit 1` 로 막는다. 유효 캡은 `AGK_CONVERSATION_JOURNAL_HARD_CAP_MB` → 러너가 선언한 기본값
→ 제품 기본값(512) 순으로 해석한다 — **러너가 선언을 멈추면 이 점검은 더 엄격해진다**(위험한 방향이 아니다).
자기시험에 6건을 추가해 양방향을 고정했다: 캡 1 MiB 면 빨개지고(그 항목을 문장으로 지목),
캡 8192 MiB 면 초록이며 투영·캡을 숫자로 보여준다. **70/70 passed**.

**2차 실행(조치 뒤)은 다시 멈췄다 — 이유는 §3f 다.** `2026-09-17T00:15:16Z` 시작 → **SC-3 에서 무한 대기** →
`00:22:48Z` 에 중단(`exit: 143`). preflight 는 **6/6 OK** 였다(처리량 437 ops/s · 투영 4,050 MiB < cap 8,192 MiB) —
즉 이 날 두 사각지대(처리량 하한 · 쓰기량 상한)를 지나온 뒤에 **세 번째 사각지대**를 만나 멈춘 것이다.
작업디렉터리 `/tmp/nx10-soak-work-20260917T001516Z`(부분 산출물은 증거로 남겼다).

**남은 교훈(다음 사람)**: 수정이 빨라지면 **쓰기량이 새 한계에 닿는다.** 리허설의 초록은 “그 트리·그 속도의
초록”이고, 어떤 최적화든 **자원 상한(캡·디스크·fd·시간)** 과의 거리를 다시 계산해야 한다.

## 3f. 일곱·여덟 번째 결함: SC-3 경합과 **하네스 무한 대기** (2026-09-17)

§3e 의 새 실행이 시작 **13초** 뒤에 멈췄다. 로그 마지막 줄은 SC-3 의 worker 하나가 죽은 traceback 이었고,
그 뒤로 로그·작업디렉터리 쓰기가 **90초 이상 0건**, 하네스 프로세스는 살아 있지만 CPU **0.0%** 였다.
그대로 두면 8시간이 지나도 리포트가 나오지 않는다(러너는 **종료 시에만** 리포트를 쓴다).

| # | 결함 | 실측 | 고침 |
|---|---|---|---|
| ⑦ | **제품**: `ProjectRegistry` 의 **최초 생성 경로만 공유 flock 밖**이었고, 백업 회전의 임시 파일 이름이 **고정**(`projects.json.bak.tmp`)이었다 → 동시에 시작한 프로세스가 같은 이름을 쓰고, 한 쪽이 먼저 `os.replace` 로 옮기면 다른 쪽이 자기 파일을 찾지 못해 `RegistrySaveError` 로 죽는다 | SC-3 5-worker 경합에서 `FileNotFoundError: … projects.json.bak.tmp -> … projects.json.bak` · 격리 재현 **5/5 통과** → **간헐** 결함. 대화 저장소에서는 같은 종류(결정론적 tmp 이름)를 이미 고쳤다(F1) — registry 백업 회전에 같은 규칙이 남아 있었다 | 최초 생성도 `with self._locked()` 안에서 하고(경합에서 진 쪽은 이긴 쪽이 쓴 파일을 읽는다 — 같은 lock 재진입은 flock 이 막으므로 재귀하지 않는다), 백업 tmp 이름을 `.{name}.tmp-{pid}` 로 고유하게 만든다. 계약 시험 3건: 생성이 lock 을 잡는가 · tmp 이름이 프로세스별로 다른가 · 5개 프로세스 동시 생성이 안 죽는가 |
| ⑧ | **하네스**: `q.get()` 에 타임아웃이 없었다 — worker 하나가 죽으면 부모가 **영원히** 기다린다(SC-1·SC-2·SC-3 세 곳 모두 같은 형태였다) | 위 실행이 그대로 멈췄다. 하루 전 8시간 실행은 같은 경합을 안 만나서 지나갔다 — **재현이 아니라 운**으로 갈렸다 | `_collect_worker_results(q, procs, fallback)` — 상한(`WORKER_RESULT_TIMEOUT_S`, 기본 120초·`AGK_VAL02_WORKER_TIMEOUT_S` 로 조정) 안에 안 오면 그 worker 를 `terminate` 하고 **오류 1건**으로 세며 계속 간다. 리포트에 `worker_timeouts` 를 남긴다(숨은 무한 대기 금지). 계약 시험 2건 |

**왜 ⑦이 “그냥 flaky” 가 아닌가**: 이 카드의 SC-3 는 **다중 프로세스 registry 동시 수정**을 검증하는
시나리오다. 그 시나리오가 잡은 것은 테스트 장치의 허술함이 아니라 **제품 코드의 경합**이다 —
클래스 docstring 은 “모든 변경 연산은 공유 lock 아래”라고 주장하지만 **생성**은 그 계약 밖이었다.

**왜 ⑧이 더 위험했나**: ⑦은 실행을 FAIL 시키는 결함이고, ⑧은 **판정 자체를 없애는** 결함이다.
이 카드는 하루 종일 “지표는 PASS 인데 귀속이 어긋난 결과”, “설정 때문에 빨간 결과”를 다퉜는데,
“아무 결과도 없는 결과”는 그보다 한 단계 더 나쁘다 — 시간을 쓰고 아무것도 배우지 못한다.

**조치와 순서**: 고칠 곳이 코드라 지문이 움직인다 → 카드 규칙대로 **고침 → 커밋(`c522b256`) → 필수 23개
재측정 → 그 지문에서 8시간 시작** 순서로 다시 세웠다.

**3차 실행(현재)**: `2026-09-17T01:19:44Z` 시작 → 종료 예정 `09:19:43Z`(18:19 KST) · 지문 `5c90b637…` =
현재 트리 = HEAD(`c522b256`) · preflight **7/7 OK**(처리량 451 ops/s · 쓰기량 투영 4,282 MiB < cap 8,192 MiB)
· **SC-1~5 완주·오류 0**(SC-3 경합 통과 — 하루 전 같은 자리에서 멈췄던 것이 지금 지나갔다) · 작업디렉터리
`/tmp/nx10-soak-work-20260917T011943Z` · 회수는 `harvest`(`--detach` 로 창이 죽어도 살아남게).

**도구에도 이 모양의 문을 달았다**: `harvest` 가 **마지막 쓰기 이후 경과**를 보고
`NX10_HARVEST_MAX_STALL`(기본 1800초)을 넘으면 “도는 중” 이 아니라 **멈춘 것**으로 보아 `exit 6` 으로
내려온다(살았는데 아무것도 안 쓰는 상태가 하루를 삼켰다). 자기시험 **70 → 75/75**.

**다음 사람에게 남기는 교훈**: 문서화된 계약("모든 변경은 lock 아래")은 **모든 경로**를 뜻한다.
그리고 시나리오가 간헐적으로만 재현하는 결함은 "운이 좋았던 실행"과 구분되지 않으므로, 계약 시험은
**경합을 결정론적으로 잡는 축**(lock 을 잡는가 · 이름이 고유한가)을 함께 고정해야 한다.
마지막으로 **하네스의 모든 대기는 상한을 가져야 한다** — 진단 없는 무한 대기는 그 자체로 결함이다.

  `soak-schedule.log` 의 `target reached` 로 판정한다.
- 처리량 하한은 **시작 시점의 값**만 본다. 직전 실행처럼 "처음엔 빠른데 시간이 갈수록 느려지는"
  결함은 60초 값으로도 잡혔지만(정상의 1%), **비례 원인이 없는 단순 퇴행**은 못 잡는다 — 그 자리는
  8시간을 돌린 뒤의 판정이다.
- 쓰기량 투영도 **선형 가정**이다(프루브는 SC-6 만 돌리므로 실제 soak 의 초반 기울기와 다를 수 있다).
  그래서 90% 여유를 요구하고, 넘칠 때는 **왜 빨간지(507 → 거짓 FAIL)**를 함께 출력한다.
- `harvest` 는 판정까지 자동이지만 **대장 반영은 사람**이다(`GATE_LEDGER` 회수 행) — 자동화한 것은
  “끝난 뒤 판정을 빠뜨리지 않는 일”이지 “판정을 읽지 않아도 되는 일”이 아니다.
- 무응답 판정은 **마지막 쓰기 시간**에 기댄다. 쓰기가 아예 없는 정상 구간(아직 시작 전 등)에서는
  `unknown` 이 나와 문이 걸리지 않는다 — 그 구간은 프로세스 존재로만 판단한다.
- 이 도구는 아직 `docs/` 에 있다(승격 대상 후보). `scripts/` 로 옮기면 **지문이 움직이므로**
  soak 회수 뒤에 [PROMOTION_PLAN.md](PROMOTION_PLAN.md) 방식으로 옮긴다.
  등록할 곳까지 적어 두었다: [CLOSURE_RUNBOOK.md](CLOSURE_RUNBOOK.md) §5-5(이동 + `--selftest` 계약 시험
  + 검사기 `DOCS`/`REFERENCED_PATHS`/`DOCUMENTED_CLI` 등록 — 검사기를 지금 고치면 그 파일이 지문 대상이라
  **오늘 22:00 예약이 죽는다**).
- 자기시험이 **밟지 않는 경로 1개**: 러너의 *죽은 주인 잠금 물려받기*(`mv … .stale-…` 뒤 진행)는
  실제 soak 을 시작해야 밟을 수 있어 일부러 제외했다(거부 경로 ⑦은 밟었다). 그래서 실행 직전에
  `status` 의 `8시간 실행 잠금: none` 을 눈으로 확인한다.
